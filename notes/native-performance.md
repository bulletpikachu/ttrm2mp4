## Promising alternative to investigate next

The older `experimental/nv12.js` GPU packer uses Chromium's original WebGL/DOM path and packs exact NV12 bytes into an RGBA FBO, but synchronously calls `gl.readPixels` into a JS array. Its `raw-encoder.js` backend always used hardware VideoToolbox via FFmpeg (~208 fps cap). Those old experiments did NOT test asynchronous WebGL2 pixel-pack buffers with the faster native multicore x264 encoder.

Potential simpler route to 10×: keep Chromium's original asynchronous GPU command decoder (instead of native ANGLE calls on the JS thread), add an 8-slot WebGL2 PIXEL_PACK_BUFFER ring to the NV12 packer, `readPixels(..., offset=0)` into a bound PBO, `fenceSync` + `flush`, and collect completed old slots via `clientWaitSync(...,0,0)` / `getBufferSubData` while later frames simulate/draw. Submit completed tight NV12 byte arrays to native x264 through a new NAPI `encodeBytes` queue. This avoids OSR compositor/RAF pacing and synchronous readback stalls. CPU readback is allowed by the actual user objective; zero-copy was an optimization attempt, not a requirement. Runtime can still be fully offline and use the unmodified native game renderer. Do not claim any speed win until measured.
