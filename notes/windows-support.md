## Encoder selection

`--encoder auto` is the portable default. The exporter checks supported H.264 profiles and preferences, then configures, encodes and flushes an actual test frame before advancing the replay. A driver that advertises support but fails initialization is skipped. The selected configuration and failed attempts are recorded in `videoEncoding` in the export report.

When no browser configuration works, CPU FFmpeg/x264 receives raw RGBA frames from the original composited game canvas. It uses ultrafast CRF18, yuv420p and no B frames. It drains and restarts at round boundaries; encoded H.264 packets feed the same master and round writers. Audio still comes from the existing continuous offline Web Audio graph and effect mixer, followed by one master AAC encode. Individual round AAC is encoded independently; exact PCM input ranges are checked against the master before acceptance.

`--encoder ffmpeg` forces this fallback for diagnosis. Its default thread count is available CPU parallelism minus one, bounded to 1–8 (five on this machine); `--threads N` overrides it. `--encoder hardware` requires a usable browser hardware configuration. `--encoder software` tries browser software encoding and then the FFmpeg fallback. These selections are separate from `--software`, which changes WebGL rendering.

Native encoders bypass the new browser probing and fallback. Their build scripts, ANGLE/Metal/IOSurface pipeline, x264 settings, native audio and `render-fast` environment defaults were retained. No Mac quality/performance regression claim is made from these Windows tests.

## Native Windows replay pipeline

The experimental replay backend now uses native ANGLE/D3D11, the original game/Pixi shaders and AA4, GPU BT.709/NV12 composition, and native asynchronous NVENC. A bounded pool of 16 textures uses explicit D3D completion and NVENC completion events before reuse. An ordered native GL driver owns the EGL context while commands execute; synchronous WebGL queries drain and transfer ownership back to the main thread. The implementation retains error checks and rejects the previously failed no-error GL mode. NVENC uses P1, ultra-low-latency and CQP18; it is a different codec configuration from the Mac's x264 ultrafast CRF18.

`scripts/build-windows-encoder.mjs` builds the additional codec after the audio, WebGL mirror and NVENC header preparation above. `src/render.mjs --windows-encoder --native-webgl --engine electron` selects it. The fast experimental flags are recorded in the Windows defaults in `src/render-native-parallel.mjs`; the public Windows-fast launcher still uses browser video encoding and the verified native audio mixer.

MSVC exposed a shared generated-command validation bug: an unsuffixed `-2147483648` bound became unsigned and rejected valid signed GL arguments. The generator now emits floating-point bounds explicitly, preserving the same mathematical ranges. All 43,203 generated writer equivalence checks pass. The Mac driver, build and codec remain separate, but shared changes still require Mac revalidation before claiming unchanged Mac performance.

`output/windows-native-full-reference.mp4/.json` is the full serial native fidelity reference, with 160 same-run game/header PNGs and NV12 encoder inputs in `windows-native-full-reference-frames/`. Its 131.38-second time includes expensive diagnostic readbacks and PNG capture and is not a clean speed measurement. Independent checks passed:

- All 19,131 decoded round frames equal the master, all nine original frame/PCM ranges and the canonical complete PCM hash match the portable baseline.
- Exact full-match A/V timestamps and sample coverage pass, with only the expected final AAC padding.
- All 160 decoded/input comparisons pass the unchanged 40 dB requirement; minimum YUV PSNR is 46.58 dB.
- All 160 original game/header PNGs independently converted on the CPU agree with the actual GPU NV12 composition above 40 dB; minimum is 58.35 dB.

It retains the existing deterministic random streams and prior-round warmup, and verifies every worker's complete timeline and PCM against a leader. ## Optional Windows shader cache

The local Windows WebGL build now includes an optional `EGL_ANDROID_blob_cache` implementation. This extension persists compiled shader blobs across executions; it does not cache replay video or alter the game shaders. Callback registration occurs once per EGL display before game contexts are created, and callbacks stay entirely native because EGL may invoke them on driver threads. See the [Khronos specification](https://registry.khronos.org/EGL/extensions/ANDROID/EGL_ANDROID_blob_cache.txt).

Cache namespaces include a SHA-256 of the actual linked ANGLE libraries, the ANGLE vendor/version, adapter identifiers and driver version queried through `IDXGIAdapter::CheckInterfaceSupport` using `IDXGIDevice` ([Microsoft documentation](https://learn.microsoft.com/en-us/windows/win32/api/dxgi/nf-dxgi-idxgiadapter-checkinterfacesupport)). Entries retain the exact opaque driver key and a SHA-256 over the key/value bytes, use bounded lengths, atomic publication and a bounded in-memory cache. Corrupt entries become cache misses and recompile through the original driver; they are never passed to it. Disk pruning applies only to shader entry files in the current namespace. Cache I/O counters are reported, and an explicitly requested cache fails early if the local binding lacks support.

After rebuilding with `node scripts/build-windows-webgl.mjs`, the experiment is enabled by an absolute local cache directory:

```powershell
$env:REPLAY_WINDOWS_SHADER_CACHE=(Join-Path (Get-Location) 'client/windows-shader-cache')
# Keep the previously documented batch/CAVLC/V8 settings for this comparison.
npm run render-native-parallel -- C:/path/example.ttrm output/match.mp4 --backend windows --jobs 2
```

## Direct3D 12 interop and single-frame NVENC probe

The isolated probe `windows-d3d12-probe.cc` creates a D3D12 device on ANGLE's existing adapter, creates committed shared BGRA/NV12 textures, opens them in ANGLE's D3D11 device and renders through the original GL interface. A shared D3D11 fence is opened in D3D12, whose queue waits for the GL writes before diagnostic readback. There is no `glFinish` between the shared-texture writes and this copy. Microsoft documents the [shared-resource/fence interop](https://learn.microsoft.com/en-us/windows/win32/api/d3d12/nf-d3d12-id3d12device-createsharedhandle); NVIDIA describes [explicit input/output fences for D3D12 encoding](https://developer.nvidia.com/blog/encoding-for-directx-12-with-video-codec-sdk-11-1/).

Both formats pass the actual known-pixel readback and leave the original context usable. The probe then opens NVENC on the D3D12 device, registers the same committed texture plus a D3D12 readback output buffer, submits D3D12 input/output resource wrappers and fences, and checks the encoded frame's timestamp. Its pinned 12.1 header requires `NV_ENC_INITIALIZE_PARAMS::bufferFormat` specifically for D3D12; leaving it unset initially returned invalid-parameter status 8. Setting it explicitly fixed initialization without changing other encoding settings.

The resulting H.264 frames decode correctly: BGRA produced 443 bytes and RGB [63,126,189] versus expected [64,127,191]; NV12 produced 439 bytes and Y/U/V [64,127,191], matching the written planes. The report is `output/windows-d3d12-nvenc-probe.json`. The earlier interop-only report is `output/windows-d3d12-interop-probe.json`.
