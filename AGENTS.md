## Desktop development and packaging

- The desktop app uses a sandboxed UI with a narrow preload bridge. The render worker uses bundled Electron in Node mode, and hidden rendering windows use normal Electron mode. Keep app resource paths and generated native loaders relative to their packages so moved builds still work.
- First-run setup uses a fresh browser session to download and verify a pinned client, then runs an offline preview before selecting it. Keep the previous cache selected if refresh fails or is cancelled. Store versioned game files, preferences, appearance imports and decoded audio in the user's application-data directory. Keep the installed game and account separate from setup.
- Appearance imports apply to all backends, including the automatic startup check. TPSE support covers static skins, textures, rank icons, particles, the first embedded still background and sound effect banks. Animated assets and custom music are skipped.
- Run `npm run package:desktop` to create an unsigned, installer-free app in `dist/`. Build native modules on the target platform before packaging if the app should include native acceleration. Automatic can use the bundled compatible browser when native modules are unavailable. The packaged app bundles the runtime and does not require Node, Chrome or compiler tools on the user's machine.
- On hybrid Windows systems, the native renderer selects the NVIDIA adapter. Rerun `prepare-windows-fast` before repackaging with updated native modules. The packager rejects ANGLE and NVENC binaries that predate the adapter fix. Distribute the whole `dist/ttrm2mp4-win32-x64` folder and extract it together before launching `ttrm2mp4.exe`.
- Mac native and compatible packaged exports were exercised after moving the app to a path with spaces. Windows desktop and packaged export still need validation on Windows hardware. Release signing and automatic updates are unconfigured.

## Native renderer setup

Use the full dependencies (`npm ci`) and prepare the local client before building either native backend. Apple Silicon needs Xcode Command Line Tools and the native development dependencies. Windows x64 needs a working NVIDIA NVENC GPU, Visual Studio C++ Build Tools and the Windows SDK.

```sh
npm ci
npm run prepare-client -- example.ttrm
# Apple Silicon macOS
npm run prepare-fast -- example.ttrm
# Windows x64 with NVIDIA NVENC
npm run prepare-windows-fast -- example.ttrm
```

- Use `npm run render -- example.ttrm output.mp4` for automatic selection or call `render-fast` (Mac) or `render-windows-fast` (Windows) directly. Preparation builds native modules and warms the cache with exact decoded browser audio samples. Each export renders its video from the replay.
- Windows source builds locate Visual Studio through `vswhere` under Program Files and discover the SDK through the environment or registry. Nonstandard installations can set `REPLAY_VSWHERE`, `REPLAY_MSVC_ROOT`, `REPLAY_WINDOWS_SDK`, `REPLAY_WINDOWS_SDK_VERSION` or `REPLAY_DELAY_LOAD_HOOK`.
- Keep the replay, cached client and dependencies fully downloaded. Use a local output destination outside cloud synchronization for comparable performance. Working media files use system scratch space. Git excludes the downloaded game files, replay inputs, compiled native modules, installers and generated exports. The official TETR.IO DMG is a wrapper for the online game. Prepare the pinned client separately for offline rendering. Client patches must fail if expected source code changes.

## Renderer selection and diagnostics

- Automatic runs a temporary 0.1-second native export at the requested size and frame rate with the requested appearance. Windows also probes concurrent NVENC sessions and Media Foundation AAC. It can retry with fewer workers when the count was chosen automatically. Failed startup checks fall back to Chrome in the CLI and to bundled Electron in the desktop app. Explicit native requests fail if startup fails. A failure during the full export stops it and leaves completed rounds in place.
- At 1080p, Windows native uses one to three drawing workers plus a continuous audio worker, reserving 2 GiB and budgeting 2 GiB per drawing worker. Mac uses one drawing worker and one to sixteen x264 threads by default. Portable CPU encoding defaults to one to eight threads. Use `--jobs N` for Windows native and `--threads N` for Mac and portable CPU encoding. `REPLAY_X264_THREADS` can also override the Mac thread count.
- Windows `--duration` and `--round` requests use the portable backend under automatic selection. The `--rounds` list supports native Windows exports. Explicit browser and encoder options use the portable path. Use `--backend portable` to select it through the automatic launcher or `render-portable` to bypass launcher probing. Direct `render-portable` needs `--export-rounds` to save individual clips.
- Portable encoding tests browser H.264 configurations with actual frames before trying CPU x264 through bundled FFmpeg. `--encoder hardware` requires working browser hardware encoding. `--encoder ffmpeg` forces the CPU path. `--software` controls WebGL separately. Pass `--chrome PATH` to both preparation and rendering if Chrome is installed in a nonstandard location.

### Single-pass GPU plane packing

New optional `REPLAY_PACKED_NV12=1` retains the native game renderer, game shaders and AA4, but packs video in one export-conversion MRT pass. `packed-nv12.inc` allocates two process-local RGBA IOSurface planes, each width=logicalWidth/4 and full height; each RGBA pixel holds four luma bytes or two UV pairs. Chroma's unused bottom half is allocation padding. The native CPU encoder consumes ordinary NV12 row bytes and logical1920×1080 dimensions. ANGLE's official `IOSurfaceSurfaceMtl.mm` confirms configurable per-plane dimensions/format, with its Metal texture created from those attributes. ### Optional Windows shader cache

The local Windows WebGL build now includes an optional `EGL_ANDROID_blob_cache` implementation. This extension persists compiled shader blobs across executions; it does not cache replay video or alter the game shaders. Callback registration occurs once per EGL display before game contexts are created, and callbacks stay entirely native because EGL may invoke them on driver threads. See the [Khronos specification](https://registry.khronos.org/EGL/extensions/ANDROID/EGL_ANDROID_blob_cache.txt).

Cache namespaces include a SHA-256 of the actual linked ANGLE libraries, the ANGLE vendor/version, adapter identifiers and driver version queried through `IDXGIAdapter::CheckInterfaceSupport` using `IDXGIDevice` ([Microsoft documentation](https://learn.microsoft.com/en-us/windows/win32/api/dxgi/nf-dxgi-idxgiadapter-checkinterfacesupport)). Entries retain the exact opaque driver key and a SHA-256 over the key/value bytes, use bounded lengths, atomic publication and a bounded in-memory cache. Corrupt entries become cache misses and recompile through the original driver; they are never passed to it. Disk pruning applies only to shader entry files in the current namespace. Cache I/O counters are reported, and an explicitly requested cache fails early if the local binding lacks support.

After rebuilding with `node scripts/build-windows-webgl.mjs`, the experiment is enabled by an absolute local cache directory:

```powershell
$env:REPLAY_WINDOWS_SHADER_CACHE=(Join-Path (Get-Location) 'client/windows-shader-cache')
# Keep the previously documented batch/CAVLC/V8 settings for this comparison.
npm run render-native-parallel -- C:/path/example.ttrm output/match.mp4 --backend windows --jobs 2
```

`node scripts/check-windows-shader-cache.mjs` passes fresh-process hits, actual rendered pixels and uniform updates, corrupted-entry recovery, concurrent writers, and cache directories containing spaces/Unicode. The rebuilt native GPU encoder check also passes all five configurations and the unsafe-batch rejection with shader caching enabled.

### Direct3D 12 interop and single-frame NVENC probe

### Live-texture conversion and final timing

A second opt-in path adds `REPLAY_WINDOWS_COMPUTE_INPLACE=1`. It imports owned game/header textures into the existing GL texture objects, preserving initial game pixels, and updates header pixels with `texSubImage2D` so their shared backing stays intact. It converts the live resolved game texture on ANGLE's D3D11 immediate context, removing the per-frame source copies and separate conversion-device handoff. The original AA4 resolve remains. NVENC still waits on the producer GPU fence, and closure drains queued compute work before resource release.

`windows-compute-state.inc` uses Microsoft's [context-state creation](https://learn.microsoft.com/en-us/windows/win32/api/d3d11_1/nf-d3d11_1-id3d11device1-createdevicecontextstate) and [state swapping](https://learn.microsoft.com/en-us/windows/win32/api/d3d11_1/nf-d3d11_1-id3d11devicecontext1-swapdevicecontextstate) APIs to restore the original drawing pipeline around conversion. The normal per-frame GL error check is retained; the previously rejected no-error mode is still forbidden. The shared-context probe poisons the current GLES output, then redraws with its prior program, textures, vertex array and viewport to check that conversion did not break drawing state.

`windows-compute-conversion-context-state.json` records six passed cases: the three synthetic sizes above on both separate-device and shared-context paths, with **zero raw-byte differences** against the current GLES shader and successful GPU-fenced H.264 encoding. The live-texture hardware suite also passed all eight pool configurations, including exact initial-pixel preservation, snapshots, header changes, empty segments and partial round restarts.

The real-game `windows-native-inplace-preview` exported **1,203 frames / 20.05 seconds**, crossing from a complete first round into three frames of round two. All 11 native-reference samples passed at minimum **46.56 dB**; every decoded round/master frame matched; timestamps began at zero and stayed contiguous; audio covered 962,400 timeline samples plus 160 final AAC padding samples. Its PCM equals the exact prefix of the original canonical full source, with both round PCM ranges verified. Evidence is in `windows-native-inplace-preview-quality.json` and `windows-native-inplace-preview-source-verification.json`, alongside the preview/report. Preview elapsed time was not treated as a clean throughput benchmark because other functional checks ran concurrently.

The final full-match timing, `windows-native-inplace-three`, completed in **52.2359 seconds externally** (51.43 internally), with all nine round files, 19,131 reported frames, 15,304,800 source samples, the canonical PCM hash and no missing assets/client errors. This is slower than both the accepted D3D11 baseline and the separate-device converter. Its full output was **not** promoted or subjected to a new complete decoded-frame/image/audio audit after this negative timing result. Its established verification scope is the hardware suite and fully checked real-game transition preview, plus the full command's runtime integrity checks.

The original **44.4207-second / 7.18× D3D11 result remains the fully audited recommendation**. Neither compute mode is a public launcher default. The compute variants and their probes require the additional Windows SDK D3DCompiler library used by the build scripts; no CUDA SDK installation was introduced. The Mac native build/settings remain separate and were not benchmarked on this Windows machine.
